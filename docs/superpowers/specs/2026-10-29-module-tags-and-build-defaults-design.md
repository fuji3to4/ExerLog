# モジュールのタグとビルド時の初期 ON/OFF 設計

日付: 2026-10-29
状態: 承認済み

## 背景と目的

Lymly は、記録アプリ ExerLog（`upstream` = `fuji3to4/ExerLog`）をリンパ浮腫向けに特化させるためにフォークしたものである。その後 OSS として公開することにしたため、一般化も考えるようになった（ユーザーの言葉）。

記録モジュールは設定画面で ON/OFF と並べ替えができるようになっている（`docs/superpowers/specs/2026-10-27-record-modules-foundation-design.md`）。それなら、リンパ浮腫向けのモジュールを ExerLog 本体に入れても、使わない人は OFF にすればよい。そこで、リンパ浮腫向けのモジュールには目印のタグを付ける。どのモジュールを最初から ON にするかはビルド時に決められるようにして、一般向け（ExerLog）とリンパ浮腫向け（Lymly）を同じコードから作り分けられるようにする。

この変更には、OSS を見た人に「この記録アプリはモジュールを足して自分用にできる土台だ」と伝える役目もある。ユーザーが想定しているのは、AI の助けを借りて自分でカスタマイズする人である。リンパ浮腫向けのモジュールにタグが付いていれば、それが「足し込まれたモジュールの一例」だと読み取れる。

## 作業の順番

1. **前提（この設計の範囲外）**：Lymly の今の変更を ExerLog（upstream）に戻す。これは別の作業として行う。
2. そのあと、この設計の変更を ExerLog 側で行う。

この設計書は Lymly リポジトリに置いておく。upstream に戻すときに一緒に持っていく。

1 と 2 の間には、ExerLog の公開サイトでリンパ浮腫の3モジュールが ON で表示される時期ができる。これは気にしなくてよい（ユーザーの判断）。今の GitHub Pages はユーザー自身のテスト用で、守るべき利用者はまだいないため。

## 公開先について

- 今公開されているのは ExerLog のサイト（`https://fuji3to4.github.io/ExerLog/`）だけで、これはユーザーのテスト用である。`next.config.ts` の `basePath` と `deploy.yml` の manifest の修正は `/ExerLog` に固定されている。
- リンパ浮腫向けの版をどこで公開するかは後回しにする（ユーザーの判断）。今回は「ビルド時に指定できるしくみ」を作るところまでで、Lymly 用のサイトや公開パスの切り替えは作らない。
- 将来 Lymly を同じ `fuji3to4.github.io` に公開すると、ExerLog と localStorage や IndexedDB を共有する。これはそのときに考える。

## ゴール

1. **モジュールにタグを持たせる。**
   - 記録モジュールの定義に、タグ（0個以上）を持てる項目を足す。
   - 今回作るタグは `lymphedema`（表示名「リンパ浮腫」/ "Lymphedema"）の1つだけ。
   - タグを付けるのは、セルフケア（`selfcare`）、着用（`compression`）、症状（`symptoms`）の3つ。
2. **設定画面にタグを表示する。**
   - モジュール一覧の各行で、名前のすぐ横に小さな丸いタグ（ピル型）を表示する（ユーザーが A 案を選んだ）。
   - 一覧はタグでまとめない。今と同じ1本のリストのままで、ドラッグと上下ボタンの並べ替えも今と同じ（ユーザーの判断）。
   - タグは目印で、押しても何も起きない。
3. **周径を「腕・脚周径」に改名する（ユーザーの判断）。**
   - 変えるのは表示名だけ。ja は「腕・脚周径」、en は "Arm & leg circumference"（en は私の訳）。
   - 「周径」という表示名は設定のモジュール一覧以外にも出てくる（`settings_export_circumference`、`sync_tab_Circumference`、`circumference_edit_title` など）。こうした「モジュール名として周径を指している」文言は、すべて新しい名前にそろえる。
   - 一方、「腕の周径 {count}か所」「周径（cm）」のように測る量としての「周径」は、そのままにする。
   - タグは付けない。左右差のグラフは筋トレをする人にも役に立つためで、一般向けのビルドでも最初から ON にする（ユーザーの判断）。
4. **最初に ON にするモジュールをビルド時に指定できるようにする。**
   - タグ単位で指定する。指定したタグを持つモジュールが、最初から ON になる。
   - タグの付いていないモジュールは、いつも最初から ON。
   - 何も指定しなければ、タグ付きのモジュールは最初は OFF になる。これが一般向けの ExerLog。
   - Lymly のデプロイでは `lymphedema` を指定し、今のリンパ浮腫向けの使い勝手を変えない。

## ゴールではないこと

- アプリ名・アイコン・`GOOGLE_NAMES` の切り替え。アプリ名は仮のものなので、今回は触らない（ユーザーの判断）。
- 胸囲・腹囲のモジュール。あえて入れずに、あとで「モジュールの足し方」の見本の題材にする（ユーザーの判断）。
- モジュールの足し方の手順書（CONTRIBUTING、AI 向けの説明書など）。これは別の作業にする。
- タグでの絞り込みやグループ表示。
- 設定画面でユーザーがタグを付けたり外したりすること。
- ON/OFF 設定の Google 同期。今どおり端末ごとに保存する。

## 失敗とみなすこと

- 一度設定を保存した端末で、更新したあとにモジュールが勝手に OFF になっていたり、並び順が変わっていたりする。
- 改名にあわせて内部の id・Dexie のテーブル名・スプレッドシートのタブ名まで変えてしまい、今ある記録や同期先とつながらなくなる。

## 決まっていること・制約

### 初期値が効く範囲

ビルド時の指定は「初期値」にすぎない。その端末でユーザーが一度でも ON/OFF や並べ替えをしたら、その設定が優先される。

今の保存形式は `{ order, disabled }` で、localStorage の `lymly-record-modules` に入っている。`disabled` に載っていないモジュールは ON として扱われる。初期値は次の決まりで当てはめる（私の判断）。

- **保存された設定がない端末**：タグの指定に入っていないタグ付きモジュールを、OFF として扱う。
- **保存された設定がある端末**：保存された `order` にまだ載っていないモジュール、つまりその端末にとって新しく増えたモジュールにだけ、同じ決まりを当てはめる。すでに `order` に載っているモジュールは、保存された設定のとおりにする。

**初回に保存する（私の判断）**：保存された設定がない端末では、初めて読んだときに、上の決まりで決めた設定をその場で localStorage に書き込む。新しく増えたモジュールに初期値を当てはめたときも、同じように書き込む。これで、あとからビルドの指定が変わったり指定が抜けたりしても、すでに使っている端末の表示は変わらない。保存に失敗した場合（storage がブロックされている場合など）は、今の `unsaved` と同じように、そのタブの中だけで覚えておけばよい。

こうすると、今の Lymly の利用者は何も変わらない。また、あとでタグ付きのモジュールが増えたとき、一般向けの利用者の画面にいきなり ON で出てくることもない。

保存キー `lymly-record-modules` は変えない（私の判断）。変えると今の利用者の設定が消えるため。

### 指定のしかた（私の判断）

- 環境変数 `NEXT_PUBLIC_DEFAULT_ON_MODULE_TAGS` にカンマ区切りでタグを並べる。例：`NEXT_PUBLIC_DEFAULT_ON_MODULE_TAGS=lymphedema`。
- 前後の空白は無視する。知らないタグは無視する（ビルドは失敗させない）。
- 静的書き出し（`next build` の static export）なので、値はビルド時に埋め込まれる。
- `.github/workflows/deploy.yml` では、この値を GitHub のリポジトリ変数 `vars.DEFAULT_ON_MODULE_TAGS` から渡す。こうすれば同じ workflow ファイルのまま、Lymly のリポジトリでは変数を `lymphedema` にし、ExerLog では空にできる。upstream と同期しても workflow がぶつからない。ただし Lymly にはまだ公開サイトがないので、今は「将来使える口を用意する」だけになる。
- ローカル開発用に、`.env.example` などの見本ファイルか README に1行書いておく（形は作る人に任せる）。

### タグの表示

- タグの表示名は翻訳ファイル（`ja.ts` / `en.ts`）に入れる。キーは `module_tag_<tag>` とする（私の判断）。
- タグの種類は TypeScript の文字列リテラルの union で定義し、知らないタグを付けられないようにする（私の判断）。
- 見た目は shadcn の Badge 相当の、小さな丸いタグにする。ほかの色との兼ね合いは `DESIGN.md` に合わせる。
- スクリーンリーダーで、タグの文字が名前と一緒に読まれること。スイッチの `aria-label` はモジュール名のままでよい。

### 変えてはいけないもの

- モジュール id `circumference`、Dexie のテーブル、同期のタブ名（内部名 `Circumference`）、CSV の列。
- 周径の部位の定義や、左右差の計算。

## 作る人に任せること

- タグの項目を `RecordModule`（画面側）と `RecordModuleData`（データ側）のどちらに置くか。設定の初期値の計算は、今の `resolveModuleSettings` の流れに組み込むのが自然だと思う。
- 初期値の計算を純粋な関数として切り出すかどうかと、そのテストの書き方（今のテストは Vitest、ファイルの隣に置く）。
- `registry.ts` 冒頭の「モジュールの足し方」コメントに、タグについて一言足すかどうか。
- 文言の細かい調整。たとえば周径の説明文「腕・脚の左右」は、改名すると名前と重なる。必要なら「左右を比べる」などに直してよい。
