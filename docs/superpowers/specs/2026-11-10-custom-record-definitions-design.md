# JSON の定義を読み込んで記録の種類を足す（カスタム記録） 設計

日付: 2026-11-10
状態: 設計中

## 背景と目的

運動記録アプリには、使う人が自分で記録したいものの欄がたいていない。そのため、多くの人は別のメモやスプレッドシートに記録していて、アプリを自分用にカスタマイズしにくい。

ユーザーの周りでトレーニングしている人たちからは、次のような記録をしたいという声がある。

- プロテインを飲んだ時刻
- 食事
- トレーニングの内容

今の ExerLog でも、AI でコードを書ける人なら、ソースを読ませれば記録モジュールを足せる。ただ、それができる人は限られる。

そこで、**記録したいものの定義を JSON で読み込むと、それが記録の種類として増え、時刻つきで記録を残せる**ようにする。

想定する流れ（ユーザーの説明）:

1. 本人が ChatGPT などの AI に「ExerLog でプロテインを記録したい」と頼み、定義の JSON を作らせる。
2. できた JSON を ExerLog に読み込む。
3. 「＋記録する」に新しい種類が出る。押すと入力フォームが開き、保存すると時刻つきで記録される。

役割の分担（ユーザーの判断）:

- **気軽に足す記録**は、JSON の定義で足す（この設計）。
- **機能まで足したい記録**（計算、画像、専用の画面など）は、今までどおり AI にコードを直させる。

ユーザーの評価: 「外部読み込みで追加できて、ここまでできるなら完璧」（モックアップ ①〜③ を見ての感想。下記「画面」）。

## ゴール

1. JSON の定義を読み込むと、記録の種類（以下「カスタム記録」）が1つ増える。カスタム記録は、既存の記録モジュールと同じように扱われる。
   - 「＋記録する」のメニューに出る
   - 定義から自動で作られた入力フォームで、新規作成・編集・削除ができる
   - タイムラインに出る
   - 履歴のチップと見返し画面に出る。数値の項目はグラフ、ほかの項目は一覧で見返す
   - カレンダーの印、期間のまとめ、CSV 書き出しに出る
   - Google スプレッドシートに同期される
   - 設定の「記録する項目」で ON/OFF と並べ替えができる
2. すべての記録は日時（`recordedAt`）を持つ。これは既存の土台の決まり（`2026-10-27-record-modules-foundation-design.md` のゴール 9）を引き継ぐ。
3. 定義は書き出して、ファイルでほかの人に渡せる（ユーザーの判断。トレーナーが指導している人に配る場面を想定）。
4. AI が迷わず定義を作れるように、「AI に渡す説明」をアプリからコピーできる。
5. 定義も Google に同期され、別の端末でも同じカスタム記録が使える。
6. 既存の記録のうち、作り込みのないものはカスタム記録と同じ仕組みに移す。作り込みのあるものは今のコードのまま残す（ユーザーの判断。下記「既存の記録の移行」）。

## ゴールではないもの

- 計算する項目（例: BMI）、画像・動画、項目どうしの条件分岐、専用のグラフや図。これらはコードで作るモジュールの役目とする（ユーザーの判断）。
- 1件の記録の中で、同じ形の行を何行も入れる形（例: 「60kg×10回」を3セット並べる）。JSON 版は簡易でよい（ユーザーの判断）。トレーニングの記録なら「1セット＝1件」か「種目・重さ・回数・セット数を1件に」で記録してもらう。
- URL での配布や、定義を共有するサーバー。ファイルで渡せれば十分（ユーザーの判断）。
- 作り込みのあるモジュール（身体、胸囲・腹囲、腕・脚周径、写真、着用、症状）の汎用化。
- 運動（動画）まわりの変更。
- 定義を作るアプリ内のエディタ。定義は AI か手で書いた JSON を読み込む。

## 画面

モックアップ: `.superpowers/brainstorm/1367-1794278157/content/custom-records-screens.html`（ユーザーは了承済み）。見た目は既存のデザインに合わせる。淡い色の 36px のボタンを使い、メニューは下から出るシートではなく、その場に開くドロップダウンにする。

### ① 設定 › 記録する項目

- カスタム記録は、既存のモジュールと同じ一覧に並ぶ。ON/OFF のスイッチと並べ替えも、既存のモジュールと同じように使える。行には「カスタム」の小さな印を付ける。
- カスタム記録の行には「⋯」を付け、ドロップダウンで次を選べるようにする。
  - **定義を書き出す**: 定義の JSON をファイルとしてダウンロードする。
  - **定義を削除**: 下記「定義を変えたとき・消したとき」に従う。
- 一覧の下に、次の2つのボタンを置く。
  - **＋ 定義を読み込む**: JSON ファイルを選ぶか、テキストを貼り付ける。読み込む前に、何が増えるのか（新規か更新か、名前、項目の一覧）を見せて確認する。定義が正しくないときは、どこがおかしいのかを日本語・英語で示す。この文章は AI にそのまま貼れば直してもらえる程度に具体的にする。
  - **AI に渡す説明をコピー**: 下記「AI に渡す説明」をクリップボードにコピーする。

### ② 入力フォーム

- 定義の項目を上から順に並べる。先頭は日時で、既存のフォームと同じ部品を使う。
- 項目の種類ごとの入力部品は下記「項目の種類」のとおり。
- 保存・削除・編集の流れは、既存のモジュールのフォーム（`RecordFormProps`）と同じにする。

### ③ タイムラインと履歴

- タイムラインのカードは、値の入っている項目を定義の順に「・」でつないで1行にする（例: 「30 g・ホエイ・トレ後」）。メモは2行目に出す。時間帯のラベル（朝・夜など）は、既存のカードと同じく付ける。
- 履歴の見返し画面:
  - 数値と段階スコアの項目は、それぞれ時間を横軸にした折れ線グラフにする。既存のグラフの部品と期間の選び方を使う。
  - そのほかは、新しい順の一覧にする。

## 定義の形

細かい JSON の形（キー名など）は builder に任せる。ただし、次のことは守る。

- **ID**: 英数字とハイフンの文字列。同じ端末・同じスプレッドシートの中で、カスタム記録を見分けるのに使う。既存のモジュールの ID（`wellness`、`body` など）とはぶつからないようにする。たとえば、内部では接頭辞を付けて区別する。
- **形式のバージョン**: 定義の形を将来変えられるよう、形式の版を持たせる。
- **名前**: 1つの文字列。ほかの言語の名前も任意で付けられるようにし、アプリの表示言語に合うものがあればそれを使う（私の案）。
- **アイコン**: 絵文字1文字（私の判断。アイコン名の一覧を AI に覚えさせる必要がないため）。なければ既定の絵文字にする。
- **色**: 任意。なければ、ID から決まった色の候補の中から選ぶ。
- **説明**: 任意。設定の一覧の2行目に出す。
- **項目の並び**: 各項目は、項目の ID、表示名、種類、必須かどうか、種類ごとの設定を持つ。項目の ID は、スプレッドシートの列名にも使う。
- メモ欄はすべてのカスタム記録に必ず付ける（私の判断。既存の記録がみなメモを持つため）。

### 項目の種類

| 種類 | 入力部品 | 種類ごとの設定 | 履歴での扱い | 用途の例 |
| --- | --- | --- | --- | --- |
| 数値 | 数値の入力欄 | 単位、最小、最大、刻み | グラフ | 量（g）、重さ、回数、分数 |
| 段階スコア | 1〜N のボタン（既存の体調のスコアボタンと同じ見た目） | 段階の数（既定 5）、両端の言葉 | グラフ | 体調のからだ・こころ、満腹度 |
| 1つ選ぶ | チップ | 選択肢（ID と表示名） | 一覧 | 種類、食事の区分 |
| いくつでも選ぶ | チップ | 選択肢（ID と表示名） | 一覧 | タイミング |
| はい／いいえ | スイッチ | なし | 一覧 | 空腹時か |
| 短いテキスト | 1行の入力欄 | なし | 一覧 | 種目名、食べたもの |

記録の値は、選択肢なら選択肢の ID で保存する（表示名を変えても過去の記録が崩れないように）。

## 定義を変えたとき・消したとき（ユーザーの了承済み）

- **同じ ID の定義をもう一度読み込んだら「更新」**とする。読み込む前の確認で、「更新」であることと、足される項目・なくなる項目を見せる。
- **項目を足しても、これまでの記録はそのまま残る**（足した項目は空のまま）。
- **消した項目のデータは、画面に出さずに保存を続ける**。スプレッドシートの列も残す。同じ項目 ID を戻せば、また表示される。
- **項目の ID はそのままで、種類を変えた定義は読み込まない**（私の判断）。たとえば「数値」から「1つ選ぶ」に変えた場合がこれにあたる。エラーの文章で「別の項目 ID にしてください」と案内し、AI に渡す説明にも同じことを書く。こうしておけば、1つの列の値はいつも同じ種類になり、グラフ・まとめ・同期の読み込みで種類の混ざった値を扱わずに済む。
- **選択肢を減らすのはかまわない**（私の判断）。なくなった選択肢を持つ過去の記録は、値を消さずに残す。一覧とタイムラインでは選択肢の ID をそのまま表示し、まとめの回数にも含める。
- **定義を削除しても、記録は消さない**。その種類は OFF と同じ扱いになる（「＋記録する」、タイムライン、履歴、カレンダーから消える）。同じ ID の定義を読み込み直せば元に戻る。
  - **削除は「論理削除」にする**（私の判断）。定義を端末とスプレッドシートから消すのではなく、「削除済み」の印を付けて残し、その印も同期する。こうすると、削除済みの種類もレジストリに残る。その結果、次のことが既存の OFF のモジュールと同じように動く。
    - 記録の同期は続く。
    - 全削除の対象になり、件数にも含まれる。
    - CSV 書き出しの対象にもなる。
  - 画面（「＋記録する」、タイムライン、履歴、カレンダー、設定の一覧）には、削除済みの種類を出さない。設定の一覧には、「削除した定義（記録あり）」を折りたたんで出す。そこから元に戻せるようにする（私の判断）。
  - 削除済みの定義と同じ ID の定義を読み込んだら、「更新」として扱い、削除済みの印を外す。

## 保存と同期

既存の土台の決まりに乗せる。具体的には、`RecordModuleData` と `RecordModule` の形、tombstone、`scheduleSync`、最後に書いた方を勝ちとする同期（last-writer-wins）を使う。

- **端末内の保存**: カスタム記録は、全種類をまとめて1つの Dexie のテーブルに入れる。種類の ID と日付で引けるようにする（私の案）。定義も、別の1つのテーブルに入れる。どちらも Dexie のバージョンを1つ上げて足す。値は `{ 項目ID: 値 }` の形で持つ。
- **スプレッドシート**:
  - **カスタム記録は、種類ごとに1枚のタブ**にする。列は「固定の列（id、date、recordedAt、note、updatedAt）＋項目の列」。列名で合わせる方式（`headerMode: "byName"`、身体・周径で使っているもの）を使い、項目を足せば列も増え、消した項目の列も残るようにする。タブ名は定義の ID から決まり、人が見て分かる名前にする（例: `Custom_protein`）。
  - **定義は、全種類まとめて1枚のタブ**にする。1行が1つの定義で、定義の JSON をそのまま1つのセルに入れる（私の案）。定義の削除は tombstone ではなく、上記の「削除済み」の印として同期する。全削除のときだけ、定義の行にも tombstone を付ける。
  - スプレッドシート名などの Google に見える名前は、`GOOGLE_NAMES` の決まり（作業名の「Lymly」を使わない）に従う。
- **レジストリが動的になる**: 今の `RECORD_MODULES` と `recordModuleData()` は、コードの中の固定の配列である。これを「コードのモジュール＋端末に読み込まれている定義から作るモジュール」に広げる必要がある。同期、全削除、件数、履歴の検索、設定の一覧は、どれもこのレジストリを通しているので、ここが変更の中心になる。
  - 同期の順番: 定義のタブを、記録のタブより先に同期する。別の端末で足された定義を先に取り込んでから、その記録のタブを同期するため。
  - 端末にまだ定義がなく、スプレッドシートに記録のタブだけがある場合は、定義が来るまでその記録のタブには触らない（私の判断）。
- **設定（ON/OFF と並び順）**: 今と同じく端末ごとに保存する。新しく読み込んだ定義は ON で末尾に足す。別の端末から同期で来た定義も同じ扱いにする（私の判断）。
- **CSV**: 種類ごとに1ファイル。列はスプレッドシートと同じにする。
- **全削除**（設定のデータ管理）: 削除済みの種類も含めて、カスタム記録をすべて消す。定義も消すかどうかは、既存の全削除の文言に合わせて builder が決める。

## 期間のまとめ

カスタム記録のまとめのカードは、汎用の形にする（私の判断）。

- 記録の件数を出す。
- 数値と段階スコアの項目は、平均・最小・最大を出す。
- 選択肢の項目は、選ばれた回数の多い順に出す。

## AI に渡す説明

設定からコピーする文章。AI が1回でアプリに読み込める定義を作れることを目標にする。

- 次の内容を含める。
  - 定義の形の説明
  - 項目の種類の一覧と、種類ごとの設定
  - ID の決まり
  - 完全なサンプル（プロテインの例）
  - 「JSON だけを出力すること」という指示
- 末尾に「記録したいもの: 」と書いておき、使う人がそのあとに記録したいものを書き足してから AI に渡せるようにする。
- 日本語と英語は、アプリの表示言語に合わせて出し分ける。
- 同じ内容を、リポジトリの中にも文書として置く（コードを読む AI のため。置き場所は builder に任せる）。

読み込むときの検査は、この説明と食い違わないようにする。説明に書いたことは、すべて受け付けること。

## 既存の記録の移行

ユーザーの方針: 「作り込みのあるものは今のまま残し、可能なものだけ汎用化する」。

| モジュール | 扱い | 理由 |
| --- | --- | --- |
| 体調 | 汎用の仕組みに移す | 段階スコア2つ＋メモで表せる |
| セルフケア | 汎用の仕組みに移す | 1つ選ぶ（スキンケア・運動・その他）＋数値（分）＋メモで表せる |
| 身体 | 今のまま | BMI の計算がある |
| 胸囲・腹囲、腕・脚周径 | 今のまま | 左右のグラフ、測り方の図、前回との差 |
| 写真 | 今のまま | 画像 |
| 着用 | 今のまま | 「着けた〜外した」の時間の組と、着用中の表示 |
| 症状 | 今のまま | 症状ごとに程度と部位を持つ入れ子の形 |

移す2つは、**コードに組み込んだ定義**（ビルトイン定義）として持つ（私の判断）。読み込んだ定義と同じ仕組みで、フォーム、タイムライン、履歴、まとめを作る。ただし、次の点は読み込んだ定義と違う。

- 書き出し・削除・上書きの読み込みはできない。読み込んだ定義の ID が、ビルトインの ID とぶつかることもない。
- モジュールの ID（`wellness`、`selfcare`）、タグ（`lymphedema` など）、既定の ON/OFF は、今と変えない。
- **既存のデータは消さない**。端末内のテーブル（`wellnessEntries`、`selfCareRecords`）と、スプレッドシートのタブ・列（`WellnessEntries`、`SelfCare` など）は、今の名前と形のまま使う。汎用の仕組みのほうが、ビルトイン定義ごとに「どのテーブル・タブ・列に書くか」を差し替えられるようにする。やり方は builder に任せる。
- **体調とおすすめ運動のつながりは残す**。おすすめ運動は、体調の「いまの調子」を返す入り口を通して、からだ・こころのスコアを読んでいる（`use-today-data.ts` → `mapWellnessToCondition`）。体調を汎用の仕組みに移しても、この入り口はそのまま動くようにする。
- 移したあとの体調とセルフケアの見た目は、汎用のものになってもよい（ユーザーの了承済み）。ただし、体調のスコアボタンは今の見た目を汎用の段階スコアの部品として流用するので、ほぼ変わらない見込み。

### 段階分け（私の判断）

1. 汎用の仕組みとカスタム記録（読み込み、書き出し、AI に渡す説明、同期を含む）。
2. 体調とセルフケアを、ビルトイン定義に移す。

段階1が段階2の前提になる。段階2は、段階1が動いてから同じ設計の範囲で進める。

## 残していること（builder に任せる）

- 定義の JSON の具体的なキー名と、検査の実装（スキーマのライブラリを使うかどうかを含む）。
- 汎用のフォーム、カード、履歴、まとめの部品の分け方と置き場所。ただし、既存の土台の決まり「モジュールのフォルダの中身が、ほかのモジュールに依存しない」は守る。
- 動的なレジストリの作り方と、React の画面へ変更を知らせる方法。
- i18n。カスタム記録の名前は定義の文字列をそのまま出すので、`labelKey` に頼らない形が必要になる。
