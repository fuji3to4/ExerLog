# 体調・セルフケア・胸囲・腹囲を「最初から入っているカスタム記録」にする 設計

日付: 2026-11-20
状態: 設計中

## 背景と目的

カスタム記録（`2026-11-10-custom-record-definitions-design.md`）で、ユーザーは JSON の定義を読み込んで記録の種類を足せるようになった。体調・セルフケアは「⋯」→「定義を書き出す」でひな形にできる。ただ、ひな形を作り変えて読み込むと、元の項目とは**別の**カスタム記録が増える。元の体調そのものに「食欲」を足すことはできない。

ユーザーの方針は「できるだけ汎用化したい」。そこで、JSON の定義で表せる3つ（体調・セルフケア・胸囲・腹囲）を、コードで書かれたモジュールから**最初から入っているカスタム記録**（以下「標準の定義」）に移す。書き出した定義を作り変えて同じ ID で読み込めば、その場で項目が変わるようにする。

着用と症状は、利用者の声を聞いてから決める（ユーザーの判断）。今回は対象外。

## ゴール

1. 体調・セルフケア・胸囲・腹囲は、カスタム記録と同じ汎用の仕組み（入力フォーム、タイムラインのカード、履歴、期間のまとめ、CSV、同期）で動く。コードで書かれた3つのモジュールはなくす。
2. アプリは、この3つの定義を最初から持っていて、端末に入れる。
3. ユーザーは「⋯」→「定義を書き出す」で標準の定義を書き出せる。同じ ID の定義を読み込むと「更新」になり、その場で項目が変わる。記録も同じ場所に残る。
4. 「⋯」に「初期の定義に戻す」を付ける。作り変えたあとでも、アプリに入っている元の形に戻せる。記録は消えない。
5. おすすめ運動は、体調の定義に「からだ（`physical`）」と「こころ（`mental`）」の段階スコアがある限り、今と同じように体調の記録を読む。

## ゴールではないもの

- 着用・症状の汎用化（ユーザーの判断）。身体・腕・脚周径・写真もコードのまま残す。
- **既存データの移行**。テスト版なので、体調・セルフケア・胸囲・腹囲の今の記録は消えてよい（ユーザーの判断）。
- 標準の定義の**削除・完全削除**。標準の項目は消せない。要らなければ設定で OFF にする（ユーザーの判断。「下手なバグに遭遇しそう」「おすすめもそう」）。
- 体調専用だった見た目（スコアボタン以外の作り込み、タイムラインの「体調 からだ3・こころ4」の書式など）の維持。汎用の見た目になってよい。
- セルフケアの「運動のときだけ分を入力する」という条件付きの欄。汎用の仕組みにはないので、分の欄は常に出る。

## 標準の項目とカスタム記録の違い（ユーザーの了承済み）

| | 標準の項目（体調・セルフケア・胸囲・腹囲） | カスタム記録（ユーザーが読み込んだもの） |
| --- | --- | --- |
| 「カスタム」の印 | 付けない | 付ける |
| 「⋯」→ 定義を書き出す | できる | できる |
| 同じ ID の読み込みで更新 | できる | できる |
| 「⋯」→ 初期の定義に戻す | できる（作り変えたときだけ出す） | なし |
| 削除・完全削除 | できない | できる |
| 設定の ON/OFF・並べ替え | できる | できる |
| タグ（例：セルフケアの「リンパ浮腫」） | 今のまま | なし |

## 決めたこと

### モジュール ID と定義 ID

- 定義 ID は `wellness`・`selfcare`・`girth`。
- **モジュール ID は今と同じ** `wellness`・`selfcare`・`girth` にする（`custom:` を付けない。私の判断）。設定の並び順と ON/OFF の保存、セルフケアのタグと最初は OFF になる扱い、おすすめ運動の「体調が ON か」の判定（`use-today-data.ts`）が、今の ID のまま動くようにするため。
- このため、定義 ID が `wellness`・`selfcare`・`girth` の定義は「標準の定義」として扱う。カスタム記録の読み込みで同じ ID の定義を読み込むと、標準の定義の「更新」になる。
  - 以前のひな形の書き出し（`exerlog-wellness.json` など）をそのまま読み込んで `custom:wellness` を作っていた場合、その定義の行は標準の定義の行として扱われる。テスト版なので、それでよい（私の判断）。

### 標準の定義の中身

- 今の `src/features/modules/custom/templates.ts` にある体調・セルフケアのひな形を、そのまま標準の定義にする。胸囲・腹囲を足す。
  - 胸囲・腹囲：名前「胸囲・腹囲」、説明「胸囲・腹囲の推移」（日英）、アイコン 📏、色 `#8a6d1f`。項目「胸囲」「腹囲（へその高さ）」はどちらも数値、単位 cm、30〜250、0.1 刻み、任意。名前と範囲は今の画面（`GIRTH_ITEMS`）に合わせる。
  - 体調・セルフケアのアイコンと色も、今の標準の項目に近いものにする（細部は builder に任せる）。
- 名前・説明・項目名は、日本語と英語の両方を持つ（今のひな形と同じ）。表示言語を切り替えると変わる。

### 端末への入れ方と、アプリの更新

- アプリは、起動時（定義のストアを読み込むとき）に、標準の定義の行が端末にあるか確かめる。なければ入れる。
- 入れるときの `updatedAt` は、**わざと古い固定の日時**にする（例：`2000-01-01T00:00:00+00:00`。私の案）。こうすると、どこかの端末でユーザーが作り変えた定義が、同期で必ず勝つ。
- 将来アプリが標準の定義の中身を変えるときに備え、固定の日時を「標準の定義の版」として扱う。
  - 端末の行の `updatedAt` が、アプリの知っている固定の日時のどれかと同じ、つまりユーザーが作り変えていないときは、最新の標準の定義（とその固定の日時）で置き換える。
  - ユーザーが作り変えた行（`updatedAt` が固定の日時ではない）は、置き換えない。
  - 細かい比べ方は builder に任せる。ただし、作り変えた定義をアプリの更新で上書きしないことは守る。
  - アプリの更新で置き換えるとき、新しい標準の定義が項目の種類を変えていて、端末の記録に合わない値があるなら、置き換えずに古いまま残す（私の判断）。標準の定義の項目の種類は、原則として変えない。
- 標準の定義の行に `deleted` の印が付いていても（以前のひな形のコピーを削除していた場合など）、標準の項目は画面から消さない（私の判断）。次の3つを、端末の中だけで行う。
  - 標準の定義の ID では、`deleted` の印を無視する。入れ直すときに `deleted` を外す。ユーザーが作り変えていた行なら、中身はそのまま残し、`deleted` だけを外す。
  - 標準の定義の ID に対する `RecordTypes` の tombstone（以前のコピーを完全削除したときのもの）は捨てる。残すと、わざと古い日時で入れた行が同期のたびに消され、入れ直され、そのあいだに記録が「持ち主のない記録」として消されるおそれがあるため。
  - `deleteOrphanRecords` は、標準の定義の ID の記録を消さない。

### 初期の定義に戻す

- 端末の定義が、アプリの標準の定義と違うときだけ、「⋯」に「初期の定義に戻す」を出す。
- 押すと確認を出す。文言は「{名前}の定義を初期の形に戻します。記録は消えません」。確定したら、標準の定義を `updatedAt = 今` で保存し、同期する（他の端末にも伝わるように。私の判断）。
- 戻した定義から消えた項目の値は、カスタム記録と同じく、記録の中に残る（画面には出ない）。
- 作り変えた定義で、項目の種類を変えた記録があっても、初期の定義に戻すことはできる（読み込みと違って断らない。私の判断）。戻したあと、種類が合わない値は記録の中に残るが、画面・グラフ・まとめには出ない（今の `coerceValue` の動きのまま）。そういう記録があるときは、確認の文言に「種類が合わない値は表示されなくなります（データは残ります）」と足す。
- 戻したあとは「作り変えた」扱いになる（`updatedAt` が固定の日時でないため）。アプリの更新で標準の定義が変わっても、自動では置き換わらない。これは受け入れる（私の判断。同期で戻す操作を確実に伝えるほうを優先した）。

### 削除できないようにする

- 標準の項目の「⋯」には「定義を削除」を出さない。
- `markTypeDeleted`・`purgeType` は、標準の定義の ID では何もしない。
- 設定の「全データ削除」（記録をすべて削除）は、今と同じく標準の項目の記録も消す。定義は消さない。

### 保存と同期

- 記録は、カスタム記録と同じ共通のテーブル `customRecords` に、`typeId` を `wellness`・`selfcare`・`girth` として入れる。
- シートのタブは、カスタム記録と同じ規則で `Custom_wellness`・`Custom_selfcare`・`Custom_girth` にする（私の判断。データの移行をしないので、古いタブと混ぜない）。
- 定義は `RecordTypes` タブに、ほかの定義と同じ形で入る。
- 古い Dexie のテーブル（`wellnessEntries`・`selfCareRecords`・`girthRecords`）は、Dexie の版を上げて消す。
- 古いシートのタブ（`WellnessEntries`・`SelfCare`・`Girth`）は、読みも書きもせず、消しもしない（これまでの方針どおり）。

### おすすめ運動とのつながり

- おすすめ運動は今、`wellness/condition.ts` の `getLatestConditionScores` を通して体調を読んでいる。この入り口は残し、中身だけを `customRecords`（`typeId = wellness`）の最新の記録を読むように変える。
- 体調の定義に、項目 ID `physical` と `mental` の段階スコアが**両方**あり、その日の最新の記録に両方の値が入っているときだけ、そのスコアを使う。
  - 段階の数が 5 でないときは、1〜5 に換算する（例：`1 + (値 - 1) × 4 ÷ (段階 - 1)`。私の案。四捨五入するかは builder に任せる）。
  - 条件を満たさないとき（項目を消した、種類を変えた、値が入っていない）は、体調を参照しない「標準のおすすめ」にする。体調を OFF にしたときと同じ動きで、今もある仕組み。
- 「食欲」のような項目を足すだけなら、おすすめ運動は今と同じように動く。

### 画面の見た目

- 入力フォーム、タイムラインのカード、履歴、期間のまとめは、カスタム記録の汎用の部品になる。
- 体調のスコアボタンは、汎用の段階スコアの部品（今の体調のボタンを広げたもの）なので、ほぼ変わらない。
- 設定の一覧では、標準の項目に「カスタム」の印を付けない。「⋯」には「定義を書き出す」と、作り変えたときだけ「初期の定義に戻す」を出す。

### 周りの更新

- `templates.ts` の役目は「標準の定義」に変わる（名前の変更や置き場所は builder に任せる）。
- 「AI に渡す説明」と `docs/custom-record-definitions.md` に、次の一文を足す。「`wellness`（体調）・`selfcare`（セルフケア）・`girth`（胸囲・腹囲）の ID で読み込むと、標準の項目そのものが変わります」。
- README の「身体測定項目を追加する」から `GIRTH_ITEMS` の記述を外す。また、カスタム記録の節に、標準の項目も同じように作り変えられることを書く。
- 体調・セルフケア・胸囲・腹囲のコード（`src/features/modules/wellness/`・`selfcare/`・`girth/`）は、おすすめ運動の入り口（`condition.ts`）など、まだ使うもの以外は消す。`GIRTH_ITEMS` も、ほかに使うところがなければ消す。

## 検討したやり方

| やり方 | 内容 | 結果 |
| --- | --- | --- |
| A. 最初から入っているカスタム記録にする | コードのモジュールをなくし、標準の定義を端末に入れる。同じ ID の読み込みで、その場で作り変えられる | **採用**（ユーザーの判断。「できるだけ汎用化したい」） |
| B. 中身だけ汎用にして、ほかは固定 | 画面とデータは汎用の仕組みで動くが、上書き・削除はできず、書き出しだけできる | 不採用。作り変えると別の記録が増える点が今と変わらない |
| C. 今のまま、ひな形の書き出しだけ足す（胸囲・腹囲） | 体調・セルフケアと同じく「コピーして作り変える」 | 不採用。最初に胸囲・腹囲だけこれで作ろうとしたが、ユーザーが A を選んだ |

## 残していること（builder に任せる）

- 標準の定義を、レジストリやストアのどこで「標準」と見分けるか（ID の一覧を持つ、など）。
- モジュール ID を `custom:` なしにするための、レジストリと `createCustomModule` の変更のしかた。
- 固定の日時（標準の定義の版）の持ち方と比べ方。
- 段階スコアの換算の丸め方。
- コードを消す範囲の細部と、それに伴うテストの整理。
